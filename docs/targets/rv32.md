# RISC-V RV32 Targets

Architecture-specific reference for the PPAP RISC-V port. Current targets
are QEMU virt (`qemu_rv32`) and Raspberry Pi Pico 2 RISC-V (`pico2rv`,
RP2350 Hazard3 cores).

---

## 1. Architecture Overview

| Aspect | Detail |
|--------|--------|
| ISA | RV32IMAC (Integer + Multiply + Atomic + Compressed) |
| Targets | QEMU virt (`qemu_rv32`), Raspberry Pi Pico 2 RISC-V (`pico2rv`) |
| Endianness | Little-endian |
| Word size | 32-bit |
| Registers | x0-x31 (x0=zero, x1=ra, x2=sp, x3=gp) |
| Callee-saved | s0-s11 (x8-x9, x18-x27) |
| PCB_SP_OFFSET | 48 |
| Syscall | `ecall` from U-mode (a7=number, a0-a5=args) |
| Timer | CLINT mtime/mtimecmp (QEMU) or SIO mtime (RP2350) |
| Context switch | Timer ISR checks `riscv_switch_pending`, calls `riscv_do_switch` |
| FPU | None (soft-float, ilp32 ABI) |
| Privilege | User processes in U-mode, kernel in M-mode |
| PMP | Entry 0: full RWX for U-mode (no protection yet) |
| Stack isolation | mscratch-based kernel/user stack split |
| Multi-core | Single-core (Phase RV-6 planned for dual-core) |

## 2. Toolchains

Both the kernel and user-space use GCC 15.1.0 with `-mabi=ilp32`
(soft-float).  RP2350 Hazard3 cores implement RV32IMAC — no FPU
hardware — so soft-float is the only correct ABI.

### Kernel

- **Compiler:** `riscv32-unknown-elf-gcc` 15.1.0 (prebuilt, Pico SDK tools)
- **ABI:** ilp32 (soft-float)

### User-space

- **Compiler:** `riscv32-unknown-linux-gnu-gcc` 15.1.0 (built from source)
- **Linker:** `riscv32-unknown-linux-gnu-ld` 2.44 (built from source)
- **ABI:** ilp32 (soft-float)
- **PIE:** enabled — binaries are linked with `-pie`
- **Relocations:** `R_RISCV_RELATIVE` in `.rela.dyn`, applied by the
  kernel ELF loader as `*target = addend + load_base`

The Linux toolchain is built from GNU release tarballs (binutils 2.44 +
gcc 15.1.0) in the Docker image, configured with `--with-arch=rv32imac
--with-abi=ilp32`.  This produces a soft-float PIC libgcc that links
cleanly into `-pie` binaries.  Prebuilt riscv-collab packages cannot be
used because they ship double-float (rv32gc) libgcc.

### GCC 15 / C23 compatibility

GCC 15 defaults to `-std=gnu23` (C23).  In C23, `void (*func)()` means
`void (*func)(void)` — no arguments allowed.  Legacy K&R code that
passes arguments through `()` function pointers (e.g. rogue's
`d_func`) fails with:

```
error: too many arguments to function 'dev->d_func'; expected 0, have 1
```

Fix: compile with `-std=gnu11` to restore C11 semantics where `()`
means unspecified parameters.  Applied in `build_rogue.sh`.

### Appendix: bare-metal fallback (removed)

The bare-metal toolchain fallback (`--emit-relocs`, `R_RISCV_32`,
`R_RISCV_HI20`/`R_RISCV_LO12_I` relocations) has been removed from
the ELF loader.  All RISC-V user-space binaries must use the Linux
toolchain with `-pie`.

## 3. PIC, PIE, and XIP

### Current model: XIP text + SRAM data

The unified ELF loader (`elf_load_image`) uses the `elf_text_mode()`
policy to decide per-binary whether text executes in-place (XIP) from
romfs or is copied to SRAM.  RISC-V uses XIP when the source is
XIP-capable (romfs), same as ARM/m68k.

- **Text:** XIP from romfs (no RAM cost).
- **Data:** allocated in SRAM via `mem_region_alloc(PPAP_MEM_RAM_DATA)`.
- **Stacks:** kernel + user stacks allocated separately via
  `mem_region_alloc(PPAP_MEM_RAM_STACK)`.

The old contiguous-SRAM model (text+data in one block) and bare-metal
fallback relocations (`R_RISCV_32`, `R_RISCV_HI20`/`R_RISCV_LO12_I`)
have been removed.

### RAM cost (pages, out of 116 on RP2350)

With XIP, only the data segment + stacks consume SRAM pages.  Text
stays in flash.

### ELF loader relocation

The kernel ELF loader uses split text/data address resolution for
`R_RISCV_RELATIVE` (type 3) entries from `.rela.dyn`:

- Addend in text range (< data_va): `*target = addend + text_base`
- Addend in data range (>= data_va): `*target = data_base + (addend - data_va)`

GOT entries are patched using the same split logic via the shared
`elf_reloc_got_split()` helper (also used by Xtensa).

### ePIC (Embedded PIC)

lowRISC's ePIC uses GP-relative addressing for all data access — `gp`
(x3) serves as a data base pointer, so text references data via
`gp + offset` instead of `auipc`.  This enables XIP for ET_DYN (PIE)
binaries where the compiler generates gp-relative code.

The current user-space binaries are ET_EXEC (not ePIC), so the gp
setup path is not exercised yet.  When ePIC binaries are used, the
loader sets `gp = data_base - data_va` via the trap frame.

- Spec: https://github.com/luismarques/epic-spec
- LLVM implementation: lowRISC's out-of-tree fork

## 4. Trap Handling

All traps go through `mtvec` (direct mode):

```
_trap_vector → _trap_entry (trap.S)
    │
    ├── mscratch swap (sp ↔ mscratch)
    │     ├── MPP=0 (from U-mode): swap correct, save user sp
    │     └── MPP=3 (nested M-mode): undo swap
    │
    ├── Exception path
    │     ├── ecall → syscall_dispatch
    │     └── other → riscv_exception_handler (with backtrace)
    │
    └── Interrupt path
          └── timer (cause=7) → riscv_timer_handler → sched_timer_tick
```

### Trap Frame

144-byte trap frame (36 words, 16-byte aligned): x1, x3-x31, mepc,
mstatus, user_sp, plus 3 padding words.

### Kernel/User Stack Split (mscratch)

User processes run in U-mode with their own user stack page (allocated
in `user_pages[]`).  The kernel stack (`stack_page`) is separate.

- **Trap entry:** `csrrw sp, mscratch, sp` swaps user sp with kernel
  stack top.  `mstatus.MPP` distinguishes U-mode (swap correct) from
  M-mode (nested trap, undo swap).
- **Trap exit:** if `TF_USER_SP != 0`, returning to U-mode — restore
  user sp via `csrrw`.  Otherwise returning to M-mode (no swap).
- **Context switch:** `riscv_do_switch` saves/restores trap frame on
  kernel stack.  `mscratch` is updated to the new process's
  `kernel_sp` after each switch.
- **PMP:** entry 0 allows full RWX for U-mode (no memory protection
  yet — future work).

### vfork with stack split

The child gets its own `stack_page` (kernel stack) and shares the
parent's `user_pages[]` (including user stack) at the same address.
No stack pointer relocation needed — the child's user sp references
the same memory as the parent's.  POSIX guarantees the parent is
blocked until the child calls `execve` or `_exit`.

### Syscall Restart

The `svc_restart` flag rewinds `mepc` by 4 and restores the original `a0`,
causing the `ecall` instruction to re-execute on return.

### Exec Pending

The `exec_pending` flag reloads SP from `current->sp` and updates
`mscratch` from `current->kernel_sp` before returning from the trap,
allowing `execve` to set up a fresh stack.  The old stack is freed
via `exec_free_old_stack` after the SP switch (deferred free pattern,
shared with m68k).

## 5. QEMU Target (`qemu_rv32`)

| Parameter | Value |
|-----------|-------|
| Machine | `-M virt -bios none` |
| UART | NS16550A at `0x10000000` (polled) |
| Timer | CLINT at `0x02000000` |
| RAM | `0x80000000` (512 KB used) |

**Note:** Requires custom string functions (`memcpy`, `strlen`, etc.)
because the Pico SDK toolchain generates Zcb instructions not supported
by QEMU 8.x.

---

## 6. RP2350 Target (`pico2rv`)

| Parameter | Value |
|-----------|-------|
| CPU | RP2350 Hazard3 RISC-V cores (RV32IMAC + Zcb/Xh3bm/Xh3power) |
| UART | PL011 at `0x40070000` (polled) |
| Timer | SIO mtime at `0xD0000000` + offsets |
| Flash | 4 MB QSPI via XIP (QMI) |

### Boot Sequence

1. RP2350 bootrom selects RISC-V cores
2. Watchdog disabled in `boot.S` (RP2350-specific)
3. `bootrom_state_reset(GLOBAL_STATE)` for hardware init
4. `clock_init_pll` runs from `.ramfunc` section (XIP cache issue after
   `bootrom_state_reset`)

## 8. Known Issues

- **Zcb instruction incompatibility:** Hazard3 supports Zcb, but QEMU 8.x
  does not; custom string functions are required for the QEMU target
- **pico2rv flash overflow:** FLASH_KERNEL needs bump to 164KB for
  mscratch code growth (reverted, needs re-apply)
- **ePIC gp validation:** when ePIC ET_DYN binaries are introduced, the
  gp register setup (`load_base = data_base - data_va`) needs testing
  to confirm correct gp-relative data access with XIP text
